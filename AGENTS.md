# AGENTS.md

Instructions for AI coding agents (GitHub Copilot coding agent, Claude Code, Codex, Cursor and similar) working in this repository. People can use it as the contributor checklist too.

## What this repo is
**100 Days of Computational Chemistry:** one small, working, documented command-line tool per day for chemistry students and researchers (RDKit, xTB, spectroscopy, XRD, ML and more). The plan is in `ROADMAP.md`.

## Layout
- `days/dayNN-slug/`: one day, with `README.md`, `tool.py`, `test_dayNN.py` and `example/`. `make_example.py` is there when the example data are generated.
- `template/dayNN-name/`: the scaffold that `tools/new_day.py` copies.
- `days/day10-index-page/tool.py`: builds `INDEX.md` and checks the repo conventions. CI runs it with `--check`.
- `INDEX.md` is generated. Never edit it by hand. `CHANGELOG.md` and the tables in `README.md` are edited by hand.

## Commands
```bash
pip install -r requirements.txt
python tools/new_day.py N slug                 # scaffold days/dayNN-slug/ and update the README table and badge
ruff check .
for d in days/*/; do pytest -q "$d"; done      # one day at a time: every tool file is called tool.py
python days/day10-index-page/tool.py           # rebuild INDEX.md
python days/day10-index-page/tool.py --check   # what CI runs
```
CI (`.github/workflows/ci.yml`) runs `ruff`, the structure check, the tests for each day, and a unit and uncertainty audit of every `tool.py`.

## Rules for a day
1. **Structure.** `README.md` starts with `# Day N: Title` and has `**What:**` and `**Why:**` lines, then Usage, Method, Test, Limitations and Next. `tool.py` has a docstring with usage, an `argparse` command line and `main() -> int`. Exit 0 on success, 1 when some items failed, 2 for bad input. Errors go to stderr as `error: ...`.
2. **Standalone days.** Do not import code from another day. Copy a small helper and say so in the README ("same reader as Day 11"). Prefer the standard library, then the packages in `requirements.txt`. If you add a dependency, add it to `requirements.txt` and to the `pip install` line in CI.
3. **Honest data.** Never invent measured numbers. Example data are either real and sourced, or **synthetic**: generated by a seeded `make_example.py`, and labelled synthetic in bold in the README and in the script's docstring. Print real output in the README by running the tool, not by typing it.
4. **Sourced reference data.** Any table of constants, standards or ranges must cite where it came from. Check it against the source. Tag entries you could not check, and say so in the README. Do not guess values.
5. **Tests.** Check formulas against an independent hand calculation, recover known values from synthetic data, test every error message and exit code, and test plots and CSV output. If a result is surprising, find out why. Do not loosen a test to make it pass.
6. **Uncertainty and units.** Put units in names (`_nm`, `_cm1`, `_deg`). Say what a reported uncertainty includes and what it leaves out. Check a reported uncertainty against a simulation in the tests. Use exact constants with a source comment. If `curve_fit` gets real measurement uncertainties, pass `absolute_sigma=True`.
7. **Limitations.** Write an honest Limitations section: assumptions, when the method fails, and what the tool does not check.
8. **Plots.** Use a color-blind-safe palette, label axes with units, and use `lineterminator="\n"` for CSV files.
9. **Audit.** CI runs the K-Dense Scientific Agent Skills `uncertainty-and-units` auditor. Fix its findings. After a real review, silence one with `# audit-units: ignore RULE -- reason` and keep the reason specific.

## Finishing a day
- Add the day's row to the tables in `README.md` ("What is in it so far" and "Where do I start?"). `new_day.py` already adds the Progress row and the badge.
- Add a line to `CHANGELOG.md`.
- Run `python days/day10-index-page/tool.py`, then `--check`, and commit `INDEX.md`.
- `ruff check .` and every day's tests must pass.
- One commit per day: `Day N: <tool>`. Do not backdate commits. Change an earlier day only to fix a bug, and say so in the pull request.

## In the pull request
State what you ran (lint, tests, check) and what you did **not** verify, for example instrument file formats you could not test or reference values you could not check. Use `.github/pull_request_template.md`.

## Agent skills
`docs/agent-skills.md` lists third-party skills that match the roadmap and explains how to install them safely. The project skill `.claude/skills/new-day/` walks through building a day. Skills can run code and change an agent's behavior, so read a skill before installing it and pin its version.
